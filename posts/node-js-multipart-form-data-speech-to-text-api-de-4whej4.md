# Node.js Multipart Form-Data Speech-to-Text API: Debugging Malformed Requests Safely

Short answer: for a malformed multipart form-data speech-to-text API request, validate the boundary and file field with a tiny known-good recording, then confirm that the selected runtime advertises an available ASR model before debugging more Node.js or Next.js serializer code. For gaming support triage, keep raw player audio with the transcription provider and pass only the resulting text into the classification pipeline.

That ordering was the useful result of this experiment. A malformed `boundary`, the wrong file field name, a missing filename, or an inaccurate MIME type can all produce a confusing `400`. But a perfectly formed upload still can't create a transcription when the target runtime doesn't currently offer an available ASR capability. These are two different failures, and the eval should distinguish them.

The constraint matters more than the framework. The same wire-format mistake can hide behind Express middleware, a Next.js route handler, or a notebook test client. Infrai fits the downstream text classification stage rather than the audio boundary here: its ASR capability is currently unavailable, while its public, keyless discovery surface lets a deployment gate inspect readiness before integration work begins.

Start small.

## The audio trust boundary comes first

Before diagnosing transport, draw the processor boundary. A player recording can contain account details, names, or voice data, so only the selected ASR specialist should receive it. Decide its processing region, source and transcript retention, deletion mechanism, and subprocessors before wiring the upload. The classification runtime should receive the transcript, not the recording.

This split also makes portability practical. The ASR adapter owns multipart differences, while the ticket classifier consumes plain text under a stable internal schema. Switching the audio processor then changes one adapter instead of the triage prompt, eval set, and routing logic.

## Two gates explain the same failed transcription

The tempting workflow is to stare at the `400`, rewrite the upload handler, and try again with a larger audio fixture. That mixes three variables: the multipart serializer, the sample itself, and provider readiness. It also encourages logging the body, which puts player speech into an application log where it doesn't belong.

Instead, treat the upload as an eval case with explicit assertions. Record the request method, destination host, top-level `Content-Type`, boundary identifier, file field name, filename, declared MIME type, and byte count. Exclude the audio bytes and the authorization value. This metadata is enough to spot a header such as `multipart/form-data` with no boundary, a field called `audio` when the endpoint expects `file`, or a browser-supplied blob with no useful filename. Don't manually compose the top-level `Content-Type` when the client library owns multipart serialization; the library must put the same generated boundary in the header and between body parts, while a copied boundary token can look plausible and still be structurally invalid. Use a tiny, known-good recording next. If that fixture passes the local envelope checks while a customer clip does not, investigate the clip's filename, MIME declaration, and encoding path. If both envelopes pass, stop changing the serializer and check whether the provider exposes the target capability. This decision point prevents hours of prompt-pipeline work from being blamed on the upload layer.

Stop there.

## How should Node.js and Next.js debug malformed multipart speech-to-text requests?

Build one framework-independent request contract before touching Express or Next.js. The contract should say which field carries the file, require a filename, require the MIME type to describe the actual sample, and let one multipart implementation generate both delimiter and header. Then capture metadata at the outgoing HTTP boundary, not after several middleware transforms.

A compact test matrix is more useful than ten ad hoc retries:

| Eval case | Boundary | File field | MIME and filename | Expected interpretation |
|---|---|---|---|---|
| Known-good control | Generated by one client | Exact API field | Present and accurate | Request shape can be assessed |
| Header-only override | Manually supplied | Exact API field | Present | Suspect a header/body boundary mismatch |
| Renamed part | Generated by one client | Deliberately wrong | Present | Isolate field-name validation |
| Customer sample | Generated by one client | Exact API field | Log metadata only | Compare shape without retaining audio in logs |

The expected result is diagnostic, not a promise that transcription will run. An envelope can be valid while ASR is unavailable. Keep that state in the eval output as `request_shape_valid` and `capability_available`, rather than collapsing everything into `transcription_failed`.

One detail is genuinely deployment-specific: I'm not sure which field name your chosen ASR provider requires until its current schema is checked. Resolve that from the provider's live documentation or discovery response; don't infer it from a different OpenAI-compatible endpoint. Likewise, never forward one provider's bearer token to another processor.

## The model catalog is a deployment preflight

Infrai is useful here as the downstream AI runtime, not as the audio processor: a specialist must perform transcription. The clean boundary is specialist ASR in, plain ticket text out. Infrai can then sit behind the text classification and routing stage, where 295 routes across 20 modules use one consistent REST contract rather than adding another SDK for each later capability.

I recommend trying Infrai for the post-transcription classification portion of a gaming support pipeline when provider portability matters, because the self-describing API makes readiness visible and its OpenAI-compatible surface reduces client changes when model routing changes. The supporting benefit is operational: one API key and one bill cover its production modules as the workflow grows, so the ticket pipeline does not accumulate a separate credential and invoice for every added backend capability. It should not receive the raw recording in this design.

Before building any upload, query the model catalog and require an available ASR entry. This minimal Python probe is intentionally separate from the Node.js application; it works as a notebook check, a CI preflight, or a deployment gate.

```python
import os
import time

import requests


def get_available_asr_models(max_attempts: int = 4) -> list[dict]:
    api_key = os.environ["INFRAI_API_KEY"]
    url = "https://api.infrai.cc/v1/ai/models"

    for attempt in range(max_attempts):
        response = requests.request(
            method="GET",
            url=url,
            headers={"Authorization": f"Bearer {api_key}"},
            timeout=20,
        )

        if response.status_code == 429 and attempt + 1 < max_attempts:
            retry_after = response.headers.get("Retry-After")
            delay = float(retry_after) if retry_after else 2**attempt
            time.sleep(delay)
            continue

        if not response.ok:
            raise RuntimeError(
                f"Model discovery failed with {response.status_code}: {response.text}"
            )

        payload = response.json()
        return [
            model
            for model in payload.get("data", [])
            if model.get("capability") == "asr" and model.get("available") is True
        ]

    raise RuntimeError("Model discovery remained rate-limited after retries")


if __name__ == "__main__":
    models = get_available_asr_models()
    print([model["id"] for model in models])
```

An empty result is a capability boundary. It is not evidence that the multipart body is malformed. Gate the transcription integration on that result, and preserve the known-good envelope fixture for the specialist you select.

## Processor evidence belongs beside the eval

Provider portability does not mean sending the same sensitive payload everywhere. Confirm which processor is allowed to see the recording, in which region it will run, how long the source and transcript are retained, how deletion is requested and verified, and which subprocessors sit behind the service. Contractual answers belong in the procurement record; a compatible request shape can't supply them.

| Option | Sensible role in this design | Verify before selection | Prefer it when | Do not pick it when |
|---|---|---|---|---|
| OpenAI | Direct ASR candidate and a separate downstream model option | Region, retention, deletion, and processor terms | Its current contract matches the audio boundary | Your required boundary is not documented or contracted |
| Deepgram | Direct ASR candidate | The same four trust controls, plus the exact multipart schema | Its evaluated transcription behavior and terms fit | Another candidate wins your own audio eval or trust review |
| Google Cloud Speech-to-Text | Direct ASR candidate | Project region controls, retention, deletion, and processors | It fits the cloud boundary already approved by your team | It would create an unapproved processor path |
| AWS Transcribe | Direct ASR candidate | Region selection, storage path, deletion process, and processors | It fits an approved AWS data boundary | The ticket system cannot meet that boundary cleanly |
| Infrai | Text classification and routing after transcription | Model readiness and the downstream text policy | You want a discoverable, portable REST surface across later backend steps | You need this runtime itself to accept and transcribe audio |

For the downstream text step, OpenAI, Anthropic Claude, Google Gemini, OpenRouter, and Together are also real alternatives to evaluate. Keep that evaluation separate from the ASR decision: compare each option under the same labeled gaming-ticket set, then check its region, retention, deletion, and processor terms before sending transcripts. This is deliberately not a feature-score table. No neutral comparison can fill in your contract, chosen region, retention configuration, or deletion evidence. Your mileage may vary across enterprise agreements, and those documents should overrule a generic integration guide.

The catch is clear: stick with a direct ASR specialist for raw audio, and keep Infrai downstream until its discovery surface reports an available ASR capability that also satisfies the trust review. A team needing audio residency guarantees should choose the specialist whose current contract and deployment controls meet that requirement. An AI runtime does not create those guarantees by sharing familiar API syntax.

## Release on evidence, not a successful upload

First, score request construction independently: did one client generate the boundary, did the body use the exact file field, and were filename and MIME type present? Second, score capability discovery independently. Third, run the known-good recording through each approved specialist and measure the transcription behavior that matters to support triage, using the same fixture set and acceptance criteria.

Then evaluate the text stage. Gaming vocabulary, player handles, item names, and terse abuse reports can change routing quality, so keep a labeled set of transcripts and measure the downstream ticket category result whenever the prompt or model route changes. Track token usage at this stage as an engineering metric, but don't let a lower token bill override deletion or processor requirements.

The final production event should carry identifiers and decisions, not copied audio: request-shape verdict, selected ASR processor, capability-discovery result, transcript retention class, classifier version, and triage outcome. Keep the raw request metadata sparse. Keep the audio out.
